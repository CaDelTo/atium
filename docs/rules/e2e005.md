# E2E005: Test too large

| ESLint name           | Severity | Category        | Confidence | Source | Presets |
| --------------------- | -------- | --------------- | ---------- | ------ | ------- |
| `atium/max-test-size` | info     | maintainability | high       | rule   | strict  |

The values come from the rule catalogue (03-linter.md §11.8).

## What it detects

A test with more than `maxActions` actions (by default 25) or whose callback spans more than `maxLines` lines (by default 150). An action is a call to `click`, `fill`, `goto`, `press`, `check` or `selectOption` on any object, or any command of a `cy` chain except the assertions `.should()` and `.and()`, so `cy.get("a").click()` is two actions. Actions inside a `test.step` count for the test that contains the step. Lines are the physical lines of the test's callback, from its first line to its last one, blank lines and comments included.

It does not count actions in hooks (`beforeEach`, `test.beforeAll`…), in helpers or Page Objects called from the test, or at module level: without following the calls, the rule only sees the test's own code. A test over both limits gets one finding, on the header of its callback (from its start to the start of its body).

## Why it is a problem

A long test checks many things at once. When it fails, the report points at one test with dozens of steps and you have to work out which part broke. It is slow to rerun, hard to name, and a failure early in it hides every check after it. Smaller tests, with the shared setup in fixtures or helpers, fail with a clear reason and can run in parallel.

## Examples

### Incorrect

```ts
test("checkout", async ({ page }) => {
  await page.goto("/");
  await page.getByLabel("Email").fill("ada@example.com");
  await page.getByLabel("Password").fill(password);
  await page.getByRole("button", { name: "Log in" }).click();
  // … 25 more actions: search, add to cart, edit the cart, pay, check the order
});
```

### Correct

```ts
test.beforeEach(async ({ page }) => {
  await logIn(page);
});

test("adds a product to the cart", async ({ page }) => {
  await page.getByRole("searchbox").fill("lamp");
  await page.getByRole("button", { name: "Add to cart" }).click();
  await expect(page.getByTestId("cart-count")).toHaveText("1");
});

test("pays for the cart", async ({ page }) => {
  // …
});
```

The rule has no autofix or suggestion, because only you know how to split the test.

## Options

- `maxActions` (integer, at least 0, default `25`): a test with more actions is reported.
- `maxLines` (integer, at least 1, default `150`): a test whose callback spans more lines is reported.

```js
"atium/max-test-size": ["warn", { maxActions: 40, maxLines: 200 }]
```

## When to disable it

For an end-to-end journey that must run as one test, such as a smoke test of the whole purchase flow, raise the limits for that file or disable it for the test with `// eslint-disable-next-line atium/max-test-size` placed just above the line where the test's callback starts (usually the `test(` line), and say why in the comment.
