# E2E001: Hard wait

| ESLint name          | Severity | Category    | Confidence | Source | Presets     |
| -------------------- | -------- | ----------- | ---------- | ------ | ----------- |
| `atium/no-hard-wait` | warning  | reliability | high       | rule   | recommended |

The values come from the rule catalogue (03-linter.md §11.8).

## What it detects

A wait for a fixed time instead of a condition:

- `waitForTimeout(n)` on any object, such as `page.waitForTimeout(5000)` or `frame.waitForTimeout(5000)`, anywhere in the file;
- `cy.wait(n)` with a number literal, also on a chain such as `cy.get("a").wait(500)`, anywhere in the file;
- `await new Promise(r => setTimeout(r, n))` inside a test, when the call to `setTimeout` is the whole body of the executor.

It does not report `cy.wait("@alias")`, which waits for a request, nor `cy.wait(delay)`, because without type information it cannot tell whether `delay` is a number. A promise with `setTimeout` is not reported outside a test, such as in a hook or a `sleep` helper, nor when it is not awaited, nor when it is returned (`return new Promise(...)`), even though the runner then waits for it.

## Why it is a problem

A fixed wait is either too long, and slows down every run, or too short on a slow machine or a busy CI runner, and the test fails at random. Waiting for the condition the test actually needs is both faster and stable: Playwright's web-first assertions and Cypress's `.should()` retry until the condition holds or the timeout expires.

## Examples

### Incorrect

```ts
test("logs in", async ({ page }) => {
  await page.getByLabel("Email").fill("ana@example.com");
  await page.getByRole("button", { name: "Log in" }).click();
  await page.waitForTimeout(5000);
  await expect(page.getByRole("heading", { name: "Welcome" })).toBeVisible();
});
```

### Correct

```ts
test("logs in", async ({ page }) => {
  await page.getByLabel("Email").fill("ana@example.com");
  await page.getByRole("button", { name: "Log in" }).click();
  await expect(page.getByRole("heading", { name: "Welcome" })).toBeVisible();
});
```

The rule cannot know what to wait for, so it has no autofix. It offers an editable suggestion with a `"TODO"` to fill in:

- `await page.waitForTimeout(5000)` becomes `await expect(page.getByRole("TODO")).toBeVisible()`;
- `cy.wait(500)` becomes `cy.get("TODO").should("be.visible")`;
- `cy.get("a").wait(500)` becomes `cy.get("a").should("be.visible")`.

The suggestion uses `expect` even if the file does not import it yet. The promise with `setTimeout` gets no suggestion, because the rule cannot tell which page or chain to wait on.

## Options

This rule has no options.

## When to disable it

When the wait is the behaviour under test, such as checking that a toast disappears after a set delay, or when waiting for something the test cannot observe, such as an animation without any state change in the DOM. Disable it for that line with `// eslint-disable-next-line atium/no-hard-wait` and say why in the comment.
